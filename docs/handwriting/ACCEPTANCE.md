## B. 工程检查

遵守根目录 AGENTS.md。项目标准命令：

```sh
yarn test:typecheck
yarn test:update
# 最终验收还要运行不更新快照的测试，避免 -u 掩盖回归：
yarn test:app --watch=false
# 对本次改动文件执行 ESLint / Prettier，再做 git diff --check。
```

当前 Codex 环境有 Node 和 node_modules，但没有 yarn 命令。本轮用下列等价入口执行，Kimi 若也遇到同样情况可以采用，并在日志如实记录：

```sh
node node_modules/typescript/bin/tsc --noEmit
node node_modules/vitest/vitest.mjs --update --watch=false
node node_modules/vitest/vitest.mjs run
node node_modules/eslint/bin/eslint.js --max-warnings=0 <本批JS/TS/TSX文件>
node node_modules/prettier/bin-prettier.js --check <本批文件>
git diff --check
```

- 更新快照后逐项解释差异，不能把异常外观/行为直接固化为新快照。保留与此次功能无关的现有代码。
- 笔刷算法要有数值/几何断言，UI 控件要有行为测试，状态机要有取消/竞争测试，不能只有“页面能打开”。
- 首次运行的既有失败写进 M0，后续新增失败单独标识。禁止删除/跳过失败测试来通过检查。
- 最终运行项目已有构建命令（先查 package.json 的 app 构建入口），记录缺失环境变量与日志；不得为构建成功向仓库写入真实凭据。网页手写核心不依赖云服务初始化。
- 真实硬件测试必须记录 iPad 型号、Pencil 型号、iPadOS 版本、Safari 或 PWA，最好附短录屏。桌面模拟只能标“模拟通过”。

## C. 交给 Codex review 的包

必须包含以下信息，不能只提供某个散落文件：

1. GitHub 分支/PR（若有）、base SHA、head SHA、提交顺序。
2. PROGRESS.md 的 M0–M5 状态和 A01–A20 逐项结果/证据链接。
3. changes/ 中全部修改记录，包括后续修复，记录顺序与提交对应。
4. 实际测试命令、时间、退出码、通过/失败/跳过数，关键失败日志，构建结果。
5. 新旧 `.excalidraw`、个人预设 JSON 及图形识别样本 fixture 的路径；素材须为测试数据，不包含私人内容。
6. 横竖屏截图、关键交互录屏、性能测量、未验证真机列表。
7. 所有偏离 SPEC 的决定、新依赖/许可证、已知问题及最短复现步骤。

Codex 审核顺序：数据兼容与丢失风险 → 指针/撤销/计时器 → 渲染/识别正确性 → UI 和性能 → 文档与测试证据。发现问题继续追加修改记录，不改写历史记录为“从未失败”。
