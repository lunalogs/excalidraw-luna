# 每次修改必须写记录

“每次”指每一批可独立描述和 review 的更改，不要求每敲一行就写一次。**每个实现提交和每次交付回复必须有对应记录**；未提交的中间批次也要先记录，不能最后凭记忆补一篇总报告。后续修 bug、调阈值、换算法、改测试、改文档同样适用。

记录保存为 `docs/handwriting/changes/NNNN-简短主题.md`，四位编号递增。每次更新 `PROGRESS.md` 链接。每个记录与实现放在同一提交；记录里填写“父提交/base SHA”和本次提交标题，实际 SHA 由后续记录或最终索引补充，避免要求提交记录包含自身 SHA 的循环。

不能覆盖旧记录以隐藏失败；修复用新记录引用旧问题。没有实际运行的命令写“未运行及原因”，不能虚构通过。若自动快照更新了与需求无关的内容，单独解释或恢复。

---

下面模板复制到每批新记录中：

```md
# NNNN — 本批主题

- 日期/执行者：
- 阶段：M0 / M1 / M2 / M3 / M4 / M5 / review 修复
- 父提交 / 起始 SHA：
- 本次提交标题：
- 对应需求 ID 与验收 ID：例如 BR-01、A05
- 状态：完成 / 部分完成 / 未完成

## 本批解决的问题

具体触发条件、原来行为、现在行为。不要只写“优化体验”。

## 改动文件

| 文件 | 改动及原因             | 影响面                |
| ---- | ---------------------- | --------------------- |
| 路径 | 具体函数/组件/格式变化 | 渲染/历史/存储/布局等 |

## 设计与数据兼容

关键公式/阈值、状态机、迁移策略、持久化/撤销边界；如有新依赖，写版本、许可证、体积、必要性。无则明确写无。偏离 SPEC 时列原要求、替代方案、理由和影响，不暗中改变验收标准。

## 实际验证

| 时间/环境 | 完整命令或操作 | 退出码/结果 | 证据路径 |
| --- | --- | --- | --- |
| Node/浏览器/设备版本 | 实际执行命令 | 通过/失败/未运行；统计 | 日志/截图/测试文件 |

快照差异说明：哪些预期改变，哪些被恢复，原因是什么。真机状态：具体设备/系统；或“未验证，只有桌面模拟”。

## 风险与未完成项

列可复现步骤、影响、下一步。不得把失败条目删掉或写成“不影响”而无证据。

## 下一批与交付状态

下一阶段、依赖、是否需要用户提供设备/权限。更新 PROGRESS.md 的对应状态与链接。
```

## 每次给用户/Kimi 交付回复的格式

- 本批完成的需求 ID 和一句话行为。
- 修改记录文件链接。
- 实际测试结果与未测项。
- 提交 SHA（已有时）和下一步。

最终交付另外附 base/head SHA 与完整提交列表。Codex 最后 review 也遵循相同记录规范。
